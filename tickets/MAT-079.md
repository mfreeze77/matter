## Purpose

Make integration reversible and observable at the host boundary. New profile or evaluator behavior should enter through recorded shadow and narrowly scoped modes, with pending advice and data migrations handled explicitly during rollback.

## In scope

- Shadow/advisory enablement modes, per-scope rollout and compatibility checks.
- Recovery from process failure, stale work and version rollback.

## Scope boundaries

- Deploying or modifying a downstream project as part of this planning ticket without that implementation task.
- Treating synthetic checks as evidence of live provider or user outcomes.

## Implementation

1. Define host-owned flags and supported state transitions between disabled, shadow and advisory operation.
2. Tie active workers and queued contributions to effective versions; reject work prepared under an incompatible rolled-back version.
3. Write executable recovery and rollback procedures against an isolated host fixture before any real deployment task.

## Acceptance criteria

### AC-1

Disabling a scope prevents new advisory delivery while preserving auditable observations and prior receipts under its policy.

**Verify:** Disable between assessment and dispatch and verify the pending operation obeys the declared cutoff.

### AC-2

Rollback does not reinterpret historical judgments as if the older policy produced them.

**Verify:** Prepare assessments under two versions, roll back and inspect immutable history plus current eligibility.

### AC-3

Interrupted processing resumes without duplicate state transitions or falsely confirmed delivery.

**Verify:** Terminate at declared commit/lease/send boundaries and compare recovered state with a serial reference episode.
