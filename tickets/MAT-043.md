## Purpose

Test the timing risks that chronological stepwise replay cannot establish. Interleave source changes, recovery, task switches, controls and provider completion under controlled clocks, while retaining historical evidence and rejecting results no longer eligible to affect the current assessment.

## In scope

- Deterministic schedule injection and stale-result qualification
- Availability versus event time and delivery-race evidence

## Scope boundaries

- Claims that time-gated inputs prove model ignorance of future facts
- Extrapolating simulated latency as measured live performance

## Implementation

1. Create an interleaving harness with dispatch, publication, completion, commit and delivery events whose order can be varied reproducibly.
2. Inject source revision changes, matched recovery, accepted control updates, task cancellation and new assessment versions while a provider call is outstanding.
3. Require admission and final delivery to compare captured read versions, scope and current authority; preserve rejected late results as history.
4. Measure queue delay, provider duration, cancellation response and delivery delay independently rather than collapsing them into one latency number.
5. Print chronological-pretraining and stepwise-concurrency limitations alongside run results and keep synthetic timing separate from observed provider timing.

## Acceptance criteria

### AC-1

A source edit or matching recovery before delivery prevents stale advice from being sent.

**Verify:** Explore both completion orders with a spy channel and inspect stale/invalidated receipts.

### AC-2

A current stop or correction takes effect without waiting for the semantic threshold or worker.

**Verify:** Block a provider future, issue the control event and verify immediate host-path handling.

### AC-3

Late-published historical facts are unavailable to earlier replay prefixes.

**Verify:** Run the same event-time history with different availability timestamps and compare packet manifests.
