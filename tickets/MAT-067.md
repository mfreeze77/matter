## Purpose

Implement the proposed Oil storage-owner adapter for a stable operational matter namespace in existing watcher SQLite storage. Keep immutable cognition runs as versioned assessment evidence, preserve the mailbox as transport and the ledger as authority, and explicitly reconcile source dependencies across revision/session runs.

## In scope

- One Oil-owned operational data namespace and supported schema/version migration
- Stable scoped matter identities independent of core/tree/session cognition run IDs
- Immutable assessment references with operational source/read dependency manifests
- Atomic version checks, idempotency, invalidation and projection rebuild
- Cross-session access/correspondence rules, retention and unavailable-history receipts

## Scope boundaries

- An immortal cognition RunManifest used as a matter identity
- Unmanaged table writes bypassing CognitionStore application/version validation
- Another independent matter database, competing lifecycle owner or transport mailbox
- Promotion of operational records into accepted user intent
- Migration of live downstream storage in this scaffold

## Implementation

1. Write and review an ownership/schema ADR naming Oil as the sole operational data owner, the Matter storage port it implements, the current chain.sqlite3 opener/version constraints and the exact supported migration/downgrade-refusal policy. Design the new namespace and compatibility through that owner rather than appending unmanaged tables.
2. Implement stable repository/owner-scoped matter IDs with explicit identity receipts. Keep per-tree/session/lane cognition RunManifest identity unchanged; represent task, audience, revision and session as relationships with access/continuity rules.
3. Import immutable cognition results using source store/run/event/payload digests. Materialize the exact source versions, applicable rules, audience/purpose versions, coverage and assessment dependencies into the operational namespace, with an idempotent handoff receipt.
4. Use expected-version commits and dependency invalidation in the operational namespace. A source or control change must invalidate dependent current assessments and prepared attention across referenced old runs; do not rely on run-local deps or the existing triggered advice deps=() path.
5. Define transactional boundaries for observation ingest, matter projection, invalidation and outbox preparation. Reuse the host worker/queue and mailbox through ports; do not duplicate lifecycle or transport ownership.
6. Implement backup/upgrade interruption recovery, schema refusal, projection rebuild and retention of compact audit references. If referenced history has been pruned, return explicit unavailable reconstruction rather than claiming complete replay.

## Acceptance criteria

### AC-1

A matter can persist across changed code trees and qualified session transitions while cognition manifests remain immutable and isolated.

**Verify:** Create multiple tree/session/core-version runs and link only qualified observations to one operational matter; assert unchanged run manifests, stable matter ID, explicit new assessments and refusal of unauthorized cross-audience linkage.

### AC-2

Changing a registered source invalidates affected operational assessments and pending attention imported from an older run.

**Verify:** Construct source→assessment→attention dependencies spanning two cognition runs, update the source and assert stale/withheld projections atomically; include existing empty-dependency triggered advice as a negative control requiring adapter reconstruction.

### AC-3

Existing supported stores migrate through the owner, unsupported stores refuse safely, and interrupted upgrades do not corrupt historical cognition data.

**Verify:** Run migration fixtures for empty/current/unsupported databases, crash at each declared transactional boundary, reopen with the supported adapter and compare cognition history hashes and matter projection rebuilds.

### AC-4

Idempotent replay and concurrent conflicting writes create one canonical operational history with no second lifecycle or delivery authority.

**Verify:** Apply identical and conflicting handoffs concurrently, then restart/rebuild; assert duplicate-versus-conflict outcomes, one matter identity and mailbox/ledger records unchanged except their explicitly authorized adapter operations.

## Risks

- The current store's run-local CAS/invalidation does not automatically provide cross-run dependencies; presenting it as already complete would leave stale delivery possible.
- Physical database reuse must respect the existing opener and migration policy rather than weakening schema safety.
- Overbroad durable identity can leak task or audience context across sessions; underbroad identity recreates the same annoyance per tree.
