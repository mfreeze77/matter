## Purpose

Execute independent questions together while representing actual data dependencies as separate stages. The stage plan must prevent sibling answers from becoming imaginary context, and must preserve why a dependent stage stopped when its prerequisite was invalid, stale, or unqualified.

## In scope

- Dependency graph validation, batching, explicit prerequisite gates
- Stage-specific packet construction and cancellation

## Scope boundaries

- A new general agent framework
- Free-running model-generated plans

## Implementation

1. Define a stage graph whose edges name prior judgments, required qualification and the transformation needed to construct the next packet or alternatives.
2. Group renderable questions with identical packet identity and compatible execution budgets into one batch; retain conditional questions when their condition is already explicit.
3. Reject cycles, references to siblings in the same batch, and missing prerequisite outcomes before provider dispatch.
4. Apply a recorded stop or authorized alternate branch for invalid, uncertain or expired prerequisites, without inventing a default candidate.
5. Carry deadlines and cancellation through each stage and preserve parent receipt IDs for later replay.

## Acceptance criteria

### AC-1

Questions that share a complete fixed packet use one batch without artificial sequencing.

**Verify:** Inspect a planned support/contradiction example and assert one request.

### AC-2

A stage needing fetched candidate details cannot run before the accepted selection and fetch complete.

**Verify:** Use controlled futures to inspect dispatch order and exact parent receipt binding.

### AC-3

Cycles, absent prerequisites and in-batch sibling dependencies fail clearly.

**Verify:** Submit three invalid plans and assert no provider calls and distinct validation reasons.
