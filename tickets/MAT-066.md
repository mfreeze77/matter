## Purpose

Implement an Oil-owned event adapter that supplies Matter with the complete operational episode rather than only emitted findings. Capture trusted success and explicit result semantics alongside original observations, streaming/deferred outcomes and host context changes, retaining provenance and unknown coverage.

## In scope

- Neutral typed event envelopes over existing native watcher/check/host paths
- Origin/invocation/phase identity and idempotent streamed/returned/deferred reconciliation
- Durable trusted-success handoff before recovery receipt pruning
- Parent audience, child task, workdir, source-version and temporal provenance
- Explicit complete/partial/unavailable check outcomes without inferring resolution from silence

## Scope boundaries

- Changing the intent ledger's authority classes
- Replacing the durable watcher queue or adding a failure daemon
- Treating all exit-zero output as proof that every open matter is resolved
- Provider calls or deployments during this scaffold

## Implementation

1. Map Observation fields and host-normalized events into the neutral envelope, including occurrence ID, invocation ID, operation key, audience/task identity, producer/check version, original event time, observed/available time, source hashes and omissions. Preserve source event kinds through an adapter rather than silently widening the existing watcher enum.
2. Instrument the native observation path and each check completion lane: ctx.post streaming, normal returned CheckResult, deferred work, explicit skips and unavailable results. Define a stable origin key so one finding represented in multiple lanes remains one contribution.
3. Consume record_known_success receipts using a durable cursor or atomic owner handoff that prevents the bounded recovery-file prune from deleting an unconsumed success. Store exact status_source and contained normalized workdir; reject inferred success from diagnostic text, unknown workdir or unrelated operation.
4. Add source/task/session/control-change envelopes through existing host seams, keeping authenticated controls distinct from observed or model-derived claims. Retain parent-session audience plus child task identity and preserve existing audience/task edit coalescing.
5. Define check-specific completion coverage. Only an explicit complete replacement scope or qualified corresponding success may retire an assertion; empty findings, a failed check, search no-match and absent output otherwise retain named unknown/no-finding states.
6. Add crash-safe restart/backfill behavior with an observed cutoff and idempotent input receipts. Capture late success and delayed outcomes with their original times instead of re-timing them as new failures.

## Acceptance criteria

### AC-1

A failed command followed by a corresponding trusted success reaches Matter even when the success produces no queued watcher observation or finding.

**Verify:** Run a native normalized host sequence through observe_tool and the adapter; assert one failure occurrence, one success receipt and a recoverable correspondence, including a worker restart between them.

### AC-2

The same result emitted through streaming, return and deferred bookkeeping counts once, while two distinct invocation failures count twice.

**Verify:** Replay an instrumented check fixture across all lanes and assert immutable origin/occurrence receipts and exact counts before and after duplicate replay.

### AC-3

No-finding, partial, unavailable, expected search no-match and unknown-status outputs cannot silently establish recovery.

**Verify:** Exercise each named result class beside a valid known-success control; assert explicit coverage/reason codes and only the valid success becomes recovery evidence.

### AC-4

Task/audience boundaries and recovery handoff survive concurrent writes, pruning and process interruption without consuming another task's evidence.

**Verify:** Use parent with two child tasks, distinct workdirs and concurrent success writers; interrupt around cursor persistence/pruning and verify no lost unconsumed success, no duplicate occurrence and no cross-task resolution.

## Required test cases

- Exit-zero success with no emitted finding; failed/no-finding check does not resolve
- Duplicate invocation arriving from streaming and final CheckResult
- Real repeated invocation with identical text after process restart
- Success pruning race and delayed success observed after a later failure
- Parent and two child tasks running the same command in different workdirs
- Unknown/outside workdir, numeric versus inferred status, and expected rg no-match

## Risks

- A _post-only hook misses success and empty-result semantics, leaving stale matters permanently open.
- The current success receipt retention is bounded; an after-the-fact importer can miss recovery without an atomic handoff or cursor guarantee.
- Over-normalizing command text or dropping task/workdir identity can merge unrelated operations.
