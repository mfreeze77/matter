## Purpose

Make stored and transmitted contracts portable across supported implementations. A schema revision, rule meaning change or migration must have an explicit compatibility policy and cannot silently reuse incompatible assessment or qualification state.

## In scope

- Version negotiation, extensions, canonical numeric/time encoding and migration manifests.
- Shared fixtures consumable by Python and a second language.

## Scope boundaries

- Deploying or modifying a downstream project as part of this planning ticket without that implementation task.
- Treating synthetic checks as evidence of live provider or user outcomes.

## Implementation

1. Separate structural compatibility from semantic rule compatibility and define rejection behavior for unknown required features.
2. Implement forward/backward migration fixtures with preserved IDs, evidence references and historical receipts.
3. Use the same canonical cases in a small second-language client to verify encoding and observable operation behavior.

## Acceptance criteria

### AC-1

A compatible reader preserves declared extension fields and rejects unknown required semantics.

**Verify:** Round-trip versioned envelopes through supported readers and exercise explicit incompatible-feature fixtures.

### AC-2

A migration preserves stable matter identities and can be rolled back under the documented contract.

**Verify:** Migrate a database containing corrections, unresolved associations and delivery-unknown receipts, then verify rollback or the declared one-way boundary.

### AC-3

Equivalent fixtures produce equivalent canonical hashes and outcomes in supported languages.

**Verify:** Compare Unicode, decimal, null, timestamp-offset and ordering cases using both client implementations.
