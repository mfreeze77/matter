## Identity and metadata evidence

A new three-key subject publishes one matter and three revisioned key projections
with the same operation receipt. The exact index framing includes scope,
namespace, and value without delimiter concatenation or normalization. Keys
preserve case and Unicode-normalization distinctions. The allowed namespace
configuration is immutable and its versioned digest is explicit in creation
commands. IDs are allocated before command preparation and retained for retries.

All supplied keys must already name one target for an `existing` result. The
result preserves original metadata and history even if a later proposal has a
new ID, title, or run. A bound subset is allowed, while a mixed bound/unbound set
cannot implicitly expand aliases. Domain mismatches and occupied proposed IDs
are conflicts. Initial lifecycle and supersession inputs are policy refusals.

The metadata operation only replaces optional title, description, and
extensions. Omission clears a field. A replacement with exactly equal canonical
JSON returns `unchanged` without creating a matter revision; stale no-op inputs
are still revision conflicts. Changed metadata appends one revision and leaves
all bare-reference key indexes unchanged.

Independent review reproduced a Python equality bug in the initial no-op check:
nested integer `1` compared equal to boolean `true`. The final implementation
compares canonical bytes. A regression changes nested `1/0` values to
`true/false` and back, verifying `updated` outcomes, revisions 1 through 3,
distinct snapshot digests, exact value types in history, and unchanged indexes.

Every new command has its own operation receipt. Metadata versions retain the
matter's original creation receipt, while `receipt_for` identifies the command
that committed each selected version. Exact retries of creation, metadata
successes, and stale failures return their original results after later edits.
Preparation preserves caller-supplied pins and never refreshes a stale edit.

## Transaction, scope, and recovery evidence

Two pairs of real processes execute commands prepared against the same state.
One pair competes to create a new subject; the other competes to edit one current
metadata revision. Each has one winner and one durable E_REVISION_CONFLICT.
The losing creator creates no partial matter or key. A new command prepared
against the winner returns the existing ID or advances metadata with a fresh
revision check; a replay of the losing command retains its original refusal.

The storage port's additive `lookup_identity` returns the current actual typed
occupant of `(scope_id, namespace, id)`. Tests prove that an observation already
occupying a proposed matter ID cannot be ignored merely because the subject key
resolves elsewhere. The same check prevents a wrong-kind occupant at a key-index
address from masquerading as absence. Transaction lookups require actual
current read pins and do not silently add them; foreign scopes and historical
pins are refused on this bare-reference API. Ordinary `get` behavior is unchanged.

The crash tests spawn processes and invoke `os._exit`, bypassing Python cleanup.
For both creation and metadata, termination before receipt or before commit
leaves no partial command or revision. New key bindings remain absent, or the
original metadata and indexes remain intact. Termination after commit recovers
the complete original result without rerunning the handler. Injected postcommit
acknowledgement errors explicitly report E_STORAGE_UNAVAILABLE until exact retry
recovers the journaled success.

A verified backup and new-file restore preserve all keys, original and revised
matter snapshots, creation and metadata receipts, and exact `created`, `updated`,
and `existing` results. Deliberately inconsistent but fully receipted projection
writes point to missing, wrong-kind, or mismatched-key targets. Resolution and
preparation refuse each as E_STORAGE_UNAVAILABLE without producing false absence
or a partial candidate list. These fixtures otherwise return a genuinely stored
matter and isolate the intentional fault to the key index.

## Reuse and qualification limits

Inspected the ticket-pinned
[StateCivics matters implementation](https://github.com/mfreeze77/state-civics-ai/blob/a34fcec27f353187e7a23d54788b203d13ac87c1/services/local-accountability/sar_tracker/core_import/matters.py),
including `vnorm`, `Matters.find`, `Matters.matter`, and `Matters.retitle`.
Persistent opaque IDs, zero/one/many resolution, and description changes that
preserve identity inform this implementation. Whitespace-removing uppercase
normalization, civic key schemes, placeholder-title policies, automatic alias
expansion, reviewed joins, redirects, and retirement rules remain outside the
neutral core. The existing MAT-003 port and canonical encoding were extended;
no new database, external client, or downstream deployment was introduced.

The host supplies authentication, actual authority, and truthful adapter key
semantics. An allowed key namespace declares a continuing-subject convention;
it is not proof of real-world semantic identity. Cross-scope grants and
semantic matching remain unimplemented. The assessment coexistence fixtures
are explicitly incomplete and make no evaluation or authority claims.

The reference backend assumes a host-controlled local filesystem with SQLite's
locking and synchronization requirements. Process death and injected failures
do not establish physical power-loss or distributed-storage qualification.
Occurrence grouping (MAT-006), claim/evidence semantics (MAT-007), association
(MAT-008), guarded identity changes (MAT-009), and later assessment/lifecycle
work remain their own tickets.
