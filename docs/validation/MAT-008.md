## Candidate, proposal and authority evidence

The catalog tests verify that a query binds source, subject, candidate type,
matching rule, selector, mode, and exact keys. Duplicate keys, candidate
identities and basis references are rejected. Canonical selector distinctions
such as `true` versus `1` and composed versus decomposed Unicode remain distinct.
Wrong types, self-nomination, unknown IDs, foreign scopes, altered schema
descriptors, wrong projection addresses, unexpected watches, and corrupted
stored bodies fail explicitly. Storage failures propagate without becoming
no-match or insufficient-evidence judgments.

Catalog publication does not mutate continuing matter identity keys. Exact
nomination uses any identical namespace/value key in this explicit catalog;
semantic packets retain every eligible entry. Availability gates inspect only
explicit evidence/basis observation metadata, not member identity or arbitrary
payload text. Every published member and dependency remains guarded, including
nonmatching alternatives. Reordered set inputs normalize consistently; exact
no-change publication and exact command retry preserve catalog history.

Proposal creation writes a bound evaluation receipt and immutable proposal in
one operation. External uncertainty, qualification and evaluator versions are
retained as declarations. Effective insufficiency cannot be overwritten by
the submitted confidence or result. Acceptance verifies the full immutable
proof and reconstructs its decision against the original current catalog,
then checks the independently injected host policy. The caller must retain
the complete considered candidate list, not only the selected candidate.

Authority tests use actual immutable receipts with host provenance and
`stage: authority`, admitted by the policy constructor. A different actor or
an ordinary operation receipt does not qualify. Semantic acceptance requires
the separate host-review flag; the direct denied execution is recorded as a
failure receipt, without an accepted association. This verifies the local
host boundary, not external identity-provider authentication.

## Decisions, correction and replay

Accepted associations have stable scoped subject/target/relation/capability
identities. Rejection and protection persist independently of proposal IDs.
A new command, new proposal, inflated semantic confidence, or admitted new
relation version cannot silently reattach a blocked pair. Merge protections
are symmetric; attachment/relatedness protections retain their direction and
declared capability.

A rejection atomically revokes the existing accepted edge and updates its
index with the new disposition and immutable decision receipt. Exact retry of
the earlier accepted command returns its saved historical success, but current
membership remains revoked. Closing and reopening the database preserves the
block and its receipt. An explicit release requires correction authority and
the current prior disposition; stale releases cannot overwrite newer
protection. Release preserves history and does not itself reactivate the edge.
A subsequent authorized acceptance still requires current evidence.

The competing-process acceptance test runs two independent prepared commands
against the same absent edge. Exactly one commits; the other conflicts rather
than creating duplicate membership or losing receipts. Candidate publication,
member revision and first-disposition cases separately exercise the stale and
absent-read boundaries.

## Independent integrity review

Review reproduced and corrected three stored-proof defects before final
acceptance:

1. A proposal and its copied receipt could agree with each other while the
   effective match contradicted the submitted evaluation. Pure proof checks
   now verify outcome and selection coherence, member eligibility, duplicate
   identities, subset membership and nested scopes.
2. A self-consistent proof could name a current candidate outside its referenced
   catalog. Acceptance now reconstructs the full decision from that original
   current catalog and compares all bound fields canonically.
3. A valid current edge could conceal an invalid intermediate history revision.
   History now verifies every snapshot's proposal and decision receipts,
   identity, revision ordering, creation receipt and provenance.

The positive integrity regression advances an associated matter's metadata,
then rejects and explicitly releases the old decision. Historical proposal
and receipt evidence remains readable without requiring old mutable catalog
inputs to become current. Release leaves the edge revoked. Current membership
queries also verify the complete watched projection against the actual index.
No material review finding remains within this ticket's bounded scope.

## Reuse and qualification limits

The pinned civic
[matter importer](https://github.com/mfreeze77/state-civics-ai/blob/a34fcec27f353187e7a23d54788b203d13ac87c1/services/local-accountability/sar_tracker/core_import/matters.py)
was inspected at `a34fcec27f353187e7a23d54788b203d13ac87c1`, particularly
`Matters.find`, `Matters.rejected`, conflict paths in `Matters.matter`, and
`merge_blocker`. The reused ideas are exact nominations without an automatic
equivalence decision, preserved operator rejection, and explicit protected
undo boundaries. This is an independent neutral implementation. No upstream
code was copied or upstream tests executed; no civic importer or source
authority is qualified by Matter's synthetic fixtures.

The implementation deliberately qualifies only an explicitly maintained local
catalog. Its host must publish newly covered candidates and coverage changes.
It does not discover an unpublished candidate elsewhere or prove global source
completeness. Catalog keys are host/adapter declarations, not inferred identity
facts. Source access checks use pinned metadata and do not re-fetch bytes.

Provider ranking, qualification and empirical semantic accuracy remain later
work. Matter merges, redirects and transitive protection across merged groups
belong to MAT-009. General trusted controls and epochs belong to MAT-011.
Dependency notices preserve exact before/after references but do not traverse
assessment graphs or cancel delivery; that remains MAT-016. A later catalog
change does not automatically revoke an earlier host decision. These limits
are explicit in the API documentation and do not acquire production status
from a passing synthetic example.
